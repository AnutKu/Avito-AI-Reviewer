# task-creater — AI-помощник лектора

Микросервис для **модуля C «Критерии как код»** из [концепции Avito AI Reviewer](../../Product-part/02_Исследования/04_Концепция/Концепция%20решения%20и%20скоуп%20MVP.md).

Делает две вещи:

1. **Генерирует домашнее задание из идеи.** Лектор описывает идею в пару предложений →
   сервис собирает готовое ДЗ в формате направления (для аналитики данных — бизнес-кейс
   с ролью и цифрами либо «выбери продукт, подбери метрики»): контекст, постановка,
   пункты сдачи, критерии-этапы с весами, **скрытая рубрика** и эталон.
2. **Проверяет систему оценивания агентами до того, как задание увидят студенты.**
   Несколько профилей «студентов» решают задание, **видя ровно то, что видит студент**;
   агент-грейдер оценивает каждое решение по полной (скрытой) рубрике; агент-критик,
   видя и то и другое, находит слабые места — неоднозначные/gameable формулировки,
   пересечения, **скрытые ожидания, которые нельзя вывести из брифа** (`unfair_hidden`),
   **утечку грейдинга в публичную часть** (`leaky_public`), несогласованность оценок —
   и предлагает точечные правки. **Применяет их человек.**

### Видимость: что видит студент, что — только ревьюер

Критерии показываются студенту **не полностью**: иначе задание вставляется в LLM и
получает максимум. Студент видит **бриф** — контекст, постановку, пункты сдачи,
обобщённую разбалловку («0 — нет, 50% — частично, 100% — полностью») и по каждому
критерию только `title` + вес + `student_hint` (одна фраза «что оценивается»).
Скрыто: `description` критерия, `expected_signals` (конкретные признаки сильного
ответа — цифры, формулы, обязательные пункты), детальные `rubric_levels`, эталон,
типичные ошибки, заметки для калибровки. `GET /tasks/{id}/export?view=student` отдаёт
только бриф; `view=reviewer` — всё.

Зачем: в интервью кейсодателя качество AI-ревьюера напрямую зависит от качества
рубрики («стиль как на воркшопе — +1 балл» модель понять не может). Обычно рубрику
чинят постфактум, по расхождениям на реальных работах. Здесь тот же цикл
запускается **на этапе создания задания**, на синтетических решениях, за секунды —
и заодно ловит, где бриф не даёт студенту вывести то, что скрыто требует рубрика.

## Как это работает

Валидация критериев — **агентный граф на LangGraph** (`StateGraph`). Узлы = агенты,
рёбра = поток управления; fan-out по профилям и решениям через `Send`, цикл раундов
через условное ребро после критика.

```
   идея ─┐                      ┌──────────────── apply_edits ◄─┐
         ▼  (нет критериев)     ▼   (теневое применение правок) │
      generate ──────────► prepare_round                        │
                    (есть критерии) │   round_no++, сброс аккумуляторов
                                    │ Send × профили
                                    ▼
                                solve_one   видит ТОЛЬКО бриф студента          [FAST]
                              (параллельно)   diligent / minimalist / lawyer / prober
                                    ▼
                              dispatch_grade        (fan-in барьер)
                                    │ Send × решения
                                    ▼
                                grade_one   ревью по ПОЛНОЙ (скрытой) рубрике  [FAST]
                              (параллельно)   баллы + цитата + decidable/нет
                                    ▼
                                 critic    находки + правки (было → стало)    [SMART]
                                    │       + RoundArtifact в state.rounds
                            route_after_critic
                        ┌───────────┴────────────┐
              сошлось / лимит раундов /       ещё раунд
                 лимит токенов                    │
                        ▼                         ▼
                       END                   apply_edits
```

После графа драйвер (`app/pipeline.py`) сворачивает правки всех раундов в один список
**относительно исходной рубрики** → человек accept/reject по каждой в `/decisions` →
задание версии `revised` → экспорт (Markdown / JSON).

Теневое применение: `apply_edits` между раундами меняет **копию** критериев (в
`state.working_criteria`), чтобы критик проверил, что находки действительно
закрываются. В настоящую рубрику ничего не попадает без `/decisions`.

### Граф: узлы, состояние, границы

| Узел | Тип | Что делает |
|---|---|---|
| `generate` | агент (SMART) | идея → задание с рубрикой; выполняется, только если критерии не переданы |
| `prepare_round` | служебный | `round_no++`, сброс `solutions`/`gradings` (редьюсер `add_or_reset`) |
| `solve_one` | агент (FAST), fan-out `Send` | один профиль решает задание; N параллельно |
| `dispatch_grade` | барьер | ждёт все `solve_one`, затем fan-out грейдинга |
| `grade_one` | агент (FAST), fan-out `Send` | ревью одного решения по рубрике; N параллельно |
| `critic` | агент (SMART) | находки + правки; собирает `RoundArtifact`, решает `converged`/`stop_reason` |
| `route_after_critic` | условное ребро | `END` или `apply_edits` — единственная точка решения о продолжении |
| `apply_edits` | служебный | теневое применение правок критика к копии критериев |

- **Состояние** ([`app/graph/state.py`](app/graph/state.py)) — `TypedDict`; `solutions`/`gradings`
  собираются fan-in'ом и сбрасываются в начале раунда, `rounds` растёт через `operator.add`.
- **LLM-клиент и счётчик расхода** не в состоянии, а в пер-ранном реестре по `run_id`
  ([`app/graph/runtime.py`](app/graph/runtime.py)) — в графе только сериализуемые данные.
- **Прогресс** — `graph.astream(stream_mode="values")`, каждое обновление состояния
  транслируется в `run.progress` и SSE.
- **Границы** — `recursion_limit=80`; выход по сходимости, лимиту раундов или бюджету токенов.
- **Durable-режим** — `build_validation_graph(checkpointer=...)` принимает
  `AsyncPostgresSaver` для возобновляемых прогонов; по умолчанию прогон живёт одним вызовом.

### Агенты и их инструкции

Полные промпты — в [`app/llm/prompts.py`](app/llm/prompts.py), профили решателей —
в [`app/agents/personas.py`](app/agents/personas.py).

| Агент | Модель | Видит | Ключевая инструкция |
|---|---|---|---|
| **Генератор** | smart | идею + формат | Формат по направлению (`case_study` / `metrics_design` / `coding` / `open`). Разделяет бриф и скрытую рубрику: `student_hint` без конкретики, вся конкретика ожиданий — в `expected_signals`. Сумма весов = разбалловке, числовые вводные внутренне согласованы. |
| **Решатель** `diligent_strong` | fast | **только бриф** | Выполнить всё добросовестно; тезисно (400–600 слов). |
| **Решатель** `minimalist_weak` | fast | **только бриф** | Минимум, расчёты «на глаз», выводы общими словами — заметно слабее добросовестного. |
| **Решатель** `rule_lawyer` | fast | **только бриф** | Выполнить БУКВУ пункта, где нет порога — самый дешёвый вариант; перечислить, где брифа не хватило и как это использовано. |
| **Решатель** `ambiguity_prober` | fast | **только бриф** | Решение, защитимое при одном прочтении и провальное при другом; описать развилку. |
| **Грейдер** | fast | бриф + **скрытая рубрика** | Баллы строго по `description` + `rubric_levels` + `expected_signals`; цитата-основание; не штрафовать за то, что студент не мог знать из брифа, но пометить. |
| **Критик** | smart | бриф + **скрытая рубрика** + все оценки | Проверить каждый `expected_signal` на выводимость из брифа; найти слабые места; каждой находке — `target` (`rubric` / `brief`) и `fix_suggestion`; правки (`CriterionEdit`) только для `target=rubric`. |

### Виды находок критика

`ambiguous` · `underspecified` · `gameable` · `overlapping` · `unmeasurable` ·
`missing_criterion` · `inconsistent_scoring` · `weight_imbalance` · `scope_creep` ·
**`unfair_hidden`** (скрытое ожидание не выводится из брифа) ·
**`leaky_public`** (публичная часть раскрывает грейдинг).
У каждой находки `target`: `rubric` (чинится правкой критерия) или `brief`
(чинится тем, что видит студент — правится вручную через `PATCH /tasks/{id}`).

## Запуск

Сервис — часть монорепо. Docker и конфиг — из **корня** репозитория (единый
`docker-compose.yml`, единый `.env`).

### Вариант 1. В составе стека (из корня репо)

```bash
cp .env.example .env          # LLM-доступ для task-creater — там же (или оставить fake)
docker compose up --build     # postgres + api + ui + taskcreater
# кабинет: http://localhost:8080  (методист → «AI-конструктор ДЗ»)
# Swagger: http://localhost:8080/task-creater/docs
```

Только этот сервис (+ общий postgres): `docker compose up --build taskcreater`
из корня, либо `make up` из этого каталога (обёртка над корневым compose).

### Вариант 2. Локально без докера (SQLite, оффлайн-LLM)

```bash
make install                  # uv sync --extra dev
make dev                      # uvicorn --reload, fake LLM, sqlite
```

### Сквозной сценарий

```bash
make demo                     # scripts/demo.py против http://127.0.0.1:8082
```

Проходит весь путь: идея → задание → валидация → находки → правки → решение
человека → экспорт финального задания.

### Проверялка эндпоинтов (вход → выход)

```bash
python3 scripts/probe.py                                    # дефолтная идея (Go worker pool)
python3 scripts/probe.py --format case_study --track "Аналитика данных" \
  --channel stepik --idea "Кейс: аналитик монетизации, take-rate ниже конкурентов…"
python3 scripts/probe.py --full --save ./out                # без обрезки + полные JSON в файлы
```

Только stdlib, ничего ставить не нужно. Дёргает основные эндпоинты по порядку и
печатает запрос и ответ каждого, плюс дайджест для оценки качества: **что видит
студент vs что скрыто**, `student_hint` с флагом утечки, **матрицу оценок с колонкой
spread**, находки критика с `target` (`BRIEF`/`rubric`) и «как чинить», правки
«было → стало». В `--save` пишет `06_export_student.{md,json}` и `06_export_reviewer.*`.
Флаги: `--format`, `--channel`, `--track`, `--points`, `--rounds`, `--full`, `--raw`, `--save`.

## API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/ideas` | сохранить идею курса |
| `POST` | `/tasks/generate` | сгенерировать задание (`{"idea": {...}}` или `{"idea_id": "..."}`) |
| `GET` | `/tasks/{id}` | черновик по id |
| `GET` | `/tasks/{root_id}/versions` | все версии задания |
| `PATCH` | `/tasks/{id}` | ручная правка лектором (в т.ч. брифа) → новая версия `edited` |
| `GET` | `/tasks/{id}/export?format=markdown\|json&view=student\|reviewer` | выгрузка: `student` — только бриф, `reviewer` (по умолч.) — всё |
| `POST` | `/tasks/{id}/validate` | запустить прогон валидации (async), тело — `ValidationConfigIn` |
| `GET` | `/validation-runs/{id}` | статус + результат прогона |
| `GET` | `/validation-runs/{id}/events` | SSE-поток прогресса |
| `POST` | `/validation-runs/{id}/decisions` | accept/reject правок → задание версии `revised` |
| `GET` | `/personas` | доступные профили решателей |

`CourseIdeaIn`: `idea`, `track`, `task_format` (`auto`/`case_study`/`metrics_design`/
`coding`/`open`), `audience_level`, `total_points`, `delivery_channel`, `constraints`.
`ValidationConfigIn`: `personas[]`, `max_rounds` (1–4), `token_budget`,
`model_fast`, `model_smart`, `solver_temperature`.

Результат прогона (`ValidationResult`) содержит: `rounds[]` (решения, оценки,
`score_matrix` для показа расхождений, находки, правки раунда),
`recommended_criteria` (предпросмотр рубрики), `proposed_edits` (свод относительно
исходной рубрики — именно эти id идут в `/decisions`), `open_findings`, `metrics`
(токены, стоимость в ₽, время).

## Технологический стек и модели

| Слой | Выбор | Почему |
|---|---|---|
| API | FastAPI + uvicorn | async, OpenAPI из коробки, стандарт для микросервисов |
| LLM | **litellm + instructor** | провайдер-агностик: один код для OpenAI-совместимого шлюза и родных провайдеров; `instructor` даёт валидированный по Pydantic структурированный вывод |
| Модели | 2 тира: `MODEL_FAST` (решатели, грейдер — массовые вызовы) и `MODEL_SMART` (генератор, критик — качество формулировок) | баланс цена/качество: ~85% вызовов идут на дешёвый тир |
| Оркестрация | **LangGraph `StateGraph`** ([`app/graph/`](app/graph/)) | агенты как узлы, fan-out через `Send`, условная маршрутизация цикла; из коробки — стриминг прогресса, барьеры fan-in, опциональный чекпоинтер для durable-прогонов |
| LLM-слой | litellm + instructor **внутри узлов** | LangGraph отвечает за поток, не за модели — провайдер-агностик и структурированный вывод сохраняются |
| Хранилище | Postgres + async SQLAlchemy, схема на JSONB | тело задания / конфиг / результат — документы; новые типы курсов и критериев не требуют миграций |
| Наблюдаемость | Langfuse (опционально), учёт токенов и стоимости в каждом прогоне | обоснование затрат — требование кейса |

**Рекомендуемый дефолт для эксплуатации:** шлюз vsellm.ru,
`MODEL_FAST=google/gemini-3.5-flash-lite`, `MODEL_SMART=google/gemini-3.6-flash`.
Один прогон валидации (4 профиля × 2 раунда ≈ 18 вызовов, ~25–60k токенов) стоит
единицы рублей. Прайс шлюза зашит в [`app/llm/client.py`](app/llm/client.py) и
переводится в ₽ по `TASKCREATER_RUB_PER_USD`. Смена на Claude / GPT — это правка
двух переменных окружения, код не меняется.

## Защита данных

- Сервис **не работает с персональными данными студентов и их кодом** — на входе
  только авторские идеи задания лектора; решения синтезируют агенты.
- LLM-вызовы идут через **один настраиваемый шлюз** (`TASKCREATER_LLM_API_BASE`);
  для боевого контура это внутренний шлюз Авито / self-hosted модель. Ключи —
  только из окружения, в логи не пишутся.
- Оффлайн-режим (`TASKCREATER_LLM_FAKE=1`) позволяет поднять и показать сервис
  вообще без внешних вызовов.
- Контейнер — non-root, минимальный `python:3.12-slim`.

## Масштабирование на другие курсы

- **Домен-агностик.** Ни в схемах, ни в промптах нет привязки к Go/QA/продукту —
  направление приходит полем `track`, критерии генерируются под него. Проверено на
  идеях из разных треков.
- **Новый профиль решателя** — одна запись в [`personas.py`](app/agents/personas.py),
  граф не меняется (fan-out идёт по списку профилей из состояния).
- **Новый шаг конвейера** (напр. детектор плагиата, проверка на дубли между решениями)
  — новый узел графа и ребро; остальные узлы не трогаются.
- **Новый вид находки** — один литерал в `FindingKind`, JSONB-хранилище migration
  не требует.
- **Durable / возобновляемые прогоны** — `build_validation_graph(AsyncPostgresSaver(...))`,
  прогон переживает рестарт и продолжается с последнего узла.
- **Реальное исполнение решений.** Сейчас режим LLM-only; интерфейс
  [`SolutionExecutor`](app/executor.py) заложен — подключение песочницы (Go/Python в
  контейнере с лимитами, без сети) даёт грейдеру факт компиляции и прогона тестов
  без изменения конвейера.
- **Интеграция с AI Reviewer.** `Criterion` / `TaskDraftData` — общий контракт:
  ту же рубрику, что выходит отсюда, потребляет модуль предварительного ревью работ.
- Прогоны асинхронные и версионируются — горизонтально масштабируется добавлением
  воркеров (сейчас фоновые задачи в процессе API; вынос в очередь — по нагрузке).

## Ограничения MVP

- Решения не исполняются (LLM-only) — грейдер судит по чтению кода/текста.
- Правки уровня `target=brief` критик только описывает (`fix_suggestion`) —
  автоприменяются лишь правки критериев; бриф лектор правит вручную через `PATCH`.
- Генератор может выдать всё-субъективную рубрику для аналитических кейсов — критик
  это ловит (`inconsistent_scoring`), но объективизация формулировок за человеком.
- Фоновые прогоны живут в процессе API (не переживают рестарт во время выполнения).
- Нет аутентификации — сервис рассчитан на внутренний периметр.
- `create_all` + точечный `ALTER` при старте вместо миграций (Alembic — при выходе за MVP).
- Оффлайн-режим (`fake`) даёт структурно валидные, но не содержательные ответы —
  он для демонстрации архитектуры и тестов, не для оценки качества рубрик.

# Единый кабинет — проектное решение

> **Статус:** согласовано по итогам проектной сессии, до начала разработки
> **Дата:** 3 сентября 2026
> **Зона ответственности документа:** каркас, ядро домена и оболочка кабинета. AI-ревью и AI-конструктор описаны здесь только на уровне контрактов — их владельцы отдельные.
> **Основание:** описание кейса, AS-IS, требования к MVP, Q&A с кейсодателем, ворклог JTBD, продуктовая концепция.

---

## 1. Рамки проекта

| Параметр | Решение |
|---|---|
| Срок | 5 дней, 3 разработчика |
| Формат сдачи | `docker-compose up` локально, предзаполненная демо-БД, кэш LLM-ответов; один живой вызов модели на «свежей» работе |
| Направление и ДЗ | Data Science, «Пример домашки 1 (АА)» — трекинг экспериментов в MLflow |
| Канал сдачи | GitHub: студент передаёт ссылку на ноутбук в репозитории |
| Модель | z.ai GLM-5.3-Flash через OpenAI-совместимый эндпоинт `https://api.z.ai/api/paas/v4/` |
| Стек | PostgreSQL, Python (FastAPI), Vue.js, по контейнеру на сервис, общий `docker-compose` |
| Стиль | Публичная палитра и типографика Авито поверх UI-kit; в презентации формулировка «визуально в стиле Авито», без заявки на соответствие дизайн-системе |

### Почему это ДЗ

- Три готовых решения разного уровня (слабое / среднее / хорошее) — закрывает TR-001 и DR-003 без дополнительных данных.
- HTML-ноутбуки после вычистки разметки — около 12k токенов каждый, влезают в контекст целиком.
- Формальной рубрики в условии нет, и это преимущество: её заводит методист в конструкторе критериев, что даёт живую сцену для модуля Rubric CI.
- Часть требований задания проверяется детерминированно, без модели: «не менее 20 запусков», перечень метрик, регистрация модели в MLflow Registry, фиксация seed.

### Стоимость обработки

Четырёхстадийный пайплайн — около 30k входных и 5k выходных токенов на работу. При тарифе GLM-5.3-Flash ($0.075 / $0.25 за миллион) это **примерно $0.004 за работу**. Цифра берётся не из оценки, а из логов `llm-gateway`, который считает токены по каждому вызову (NFR-022).

## 2. Границы зон и правила совместной работы

**Кабинет = каркас + ядро домена + оболочка.** Владелец кабинета поставляет: `docker-compose`, схему core-БД, auth и RBAC, контракты API, оболочку UI с ролевой навигацией и сквозной путь «сдача → снапшот → очередь → статус → результат».

Двое других владельцев приносят внутрь готовые модули: AI-ревью и AI-конструктор с Rubric CI. **Пока модули не готовы, кабинет работает на моках** — заглушка возвращает результат в том же контракте, что и настоящий пайплайн.

### Правила владения

1. Core-схему БД меняет только владелец кабинета. Фичи добавляют **свои** таблицы **своими** миграциями и не трогают core.
2. Контракты API фиксируются в OpenAPI **к обеду первого дня** и после этого меняются только по общему согласию.
3. Фронтенд — feature-sliced: каждая фича в своей папке, общие компоненты берутся только из слоя `shared/ui`, который поставляет владелец кабинета.
4. День 1 команда работает вместе над каркасом и контрактами, с вечера расходится по фичам.

### Деградация

Каждый раздел живёт за фиче-флагом в конфиге. Выключенный раздел не появляется в навигации — кабинет всегда выглядит целым. Порядок отказа применяется изменением конфига, а не вырезкой кода перед защитой.

Разделы, работающие на фикстурах, автоматически получают бейдж **«демо-данные»** — это часть того же механизма.

## 3. Роли и карта экранов

Двенадцать экранов — верхняя граница объёма на пять дней.

### Студент (4 экрана)

| Экран | Содержание |
|---|---|
| Мои задания | Список: задание, дедлайн, статус, итоговый балл |
| Задание | Условие, критерии, форма сдачи ссылки на GitHub |
| Результат | Баллы по критериям и цельный фидбэк. **Ничего про AI-сигнал** |
| Дополнительные вопросы | Блиц: вопросы и поле текстового ответа |

Смысл для студента — одно окно вместо GitHub + Stepik + Google Sheets. Он не видит распределения, черновиков, AI-сигнала и аналитики.

### Ревьюер (2 экрана)

| Экран | Содержание |
|---|---|
| Моя очередь | Работы, дедлайны, флаг риска просрочки |
| **Ревью** | Слева отрендеренный ноутбук, справа: критерии с баллами и основаниями, панель внимания, AI-сигнал, черновик фидбэка |

Экран «Ревью» — главный экран продукта. Если убрать из демо всё остальное, продукт всё ещё читается; без него не читается ничего.

### Методист (6 экранов)

| Экран | Содержание |
|---|---|
| Дашборд курса | Воронка статусов, просрочки, нагрузка ревьюеров |
| Распределение | Предложенная раскладка с объяснениями + апрув одной кнопкой |
| Реестр работ | Фильтры, ручное переназначение |
| Задания и критерии | Версии рубрик — **точка входа фичи «AI-конструктор»** |
| Аналитика | **Точка входа фич «Аналитика критериев» и «Course Debt Radar»** |
| Настройки курса | Tone of voice, кап нагрузки, дедлайны |

### Общее

Демо-логин с тремя кнопками, шапка с колокольчиком уведомлений.

## 4. Жизненный цикл работы

Два автомата, работающих параллельно, — потому что AI-ревью стартует при приёме работы, независимо от назначения ревьюера.

### Автомат работы (`submissions.status`)

```
submitted → proposed → assigned → in_review → [blitz_sent → blitz_answered] → completed
```

- `proposed` — система предложила ревьюера, ждём апрува методиста.
- `assigned` — методист применил раскладку. **Именно здесь уходят уведомления ревьюерам** — в этот момент из процесса исчезает ручной шаг модератора.
- До апрува ревьюер работу не видит.
- `completed` — терминальный статус. Цикл доработки и пересдачи в MVP свёрнут: работа, проверенная агентом и подтверждённая ревьюером, считается завершённой. На защите это проговаривается честно.

Поперечные признаки: `is_overdue` — флаг, не статус.

### Автомат AI-прогона (`reviews.ai_status`)

```
pending → running → ready | failed
```

Запускается сразу при приёме работы. К моменту, когда ревьюер открывает работу, разбор уже готов. При `failed` работа уходит ревьюеру **без** AI-результата и с понятным сообщением — никаких выдуманных ответов (NFR-010).

Все переходы пишутся в `status_history`. Из неё же считаются время обработки и доля просрочек (M-001, M-004) — отдельного учёта не требуется.

## 5. Схема данных (core)

Владелец — кабинет. Фичи добавляют свои таблицы рядом.

| Таблица | Назначение |
|---|---|
| `users` | id, email, ФИО, роль (student / reviewer / methodist), специализация, доступность |
| `courses` | id, название, tone_of_voice (jsonb), кап нагрузки на ревьюера |
| `enrollments` | связь студентов с курсом |
| `assignments` | id, курс, условие, дедлайн, вес трудоёмкости, канал сдачи |
| `rubric_versions` | id, задание, номер версии, `criteria` (jsonb), автор, дата публикации |
| `submissions` | id, задание, студент, ссылка на источник, время сдачи, статус, флаг просрочки |
| `snapshots` | id, сдача, содержимое, хэш содержимого, время загрузки, `parsed_facts` (jsonb) |
| `review_assignments` | id, сдача, ревьюер, кем предложено, текст объяснения, кем и когда утверждено |
| `reviews` | id, сдача, `rubric_version_id`, модель, `ai_status`, сырой результат AI, итоговый балл, итоговый фидбэк, кем завершено |
| `review_items` | id, ревью, `criterion_key`, балл AI, вердикт, уверенность, основания, **действие ревьюера** (принято / изменено / отклонено), итоговый балл и комментарий |
| `ai_signals` | id, ревью, тип (ai_use / understanding_risk), уровень, основания, ограничения метода, решение ревьюера |
| `blitz_sessions` | id, ревью, вопросы, отправлено, срок, ответы, разбор AI, решение ревьюера |
| `status_history` | id, сдача, откуда, куда, кто, когда |
| `notifications` | id, получатель, тип, полезная нагрузка, канал (in_app / telegram), отправлено, прочитано |
| `llm_calls` | стадия, модель, хэш промпта, токены, стоимость, попадание в кэш |

### Ключевые инварианты

- **`rubric_versions` неизменяемы.** Опубликованная версия не редактируется никогда; правка — это новая версия. Отсюда бесплатно получаются воспроизводимость (FR-026), Rubric CI (два прогона с разным `rubric_version_id`) и аналитика по стабильному `criterion_key`.
- **Снапшот решения сохраняется при приёме.** Всё ревью работает со снапшотом, повторных походов в GitHub нет. Это закрывает идемпотентность (NFR-012), воспроизводимость и спасает демо при недоступности сети.
- **`review_items.reviewer_action`** — единственный источник данных для аналитики правок. Его пишет кабинет, читают фичи аналитики.

## 6. Пайплайн AI-ревью — контракт

Четыре стадии. Первая — **детерминированная, без модели**.

| Стадия | Что делает |
|---|---|
| `extract` | Парсер ноутбука → факты: число запусков, перечень залогированных метрик, наличие регистрации модели, фиксация seed, порядок и разрывы `execution_count`, доля упавших ячеек |
| `grade` | Факты + рубрика + текст решения → баллы по критериям с основаниями |
| `signal` | Отдельным вызовом: AI-use signal и Understanding risk |
| `feedback` | Цельный текст студенту в tone of voice курса |

`grade` и `signal` разделены намеренно: смешивать «поставь балл» и «оцени признаки ИИ» в одном промпте — верный способ получить предвзятую оценку.

**Панель внимания — не отдельный вызов**, а производная: критерии с низкой уверенностью плюс сработавшие сигналы.

### Контракт по критерию

`score` · `verdict` · `confidence` · `evidence` (цитата + якорь на ячейку ноутбука) · `recommendation`

### Два слоя результата

- **Студенту** — цельный связный фидбэк, прозрачное объяснение оценки, сильные стороны и зоны улучшения.
- **Ревьюеру** — покритериальная раскладка, уровень уверенности, панель внимания с конкретными файлами и фрагментами, возможность подтвердить / изменить / отклонить **каждый** вывод отдельно.

### AI-use signal: на чём он стоит

Детерминированные признаки из ноутбука, LLM формулирует объяснение и уровень. Внешние детекторы исключены — отправка работ в сторонние сервисы запрещена (NFR-001).

Признаки: порядок и разрывы `execution_count`, доля упавших ячеек и следов отладки, наличие закомментированного кода и черновых экспериментов, стилистическая однородность markdown, разрыв «сложный код ↔ бедное объяснение» (это уже Understanding risk).

**Уровень уверенности — три градации с описанной шкалой, а не проценты.** FR-041 это допускает явно, а нарисованный процент невозможно обосновать. Рядом с сигналом обязателен блок «ограничения метода» (FR-042).

Асинхронность: ревью идёт через очередь, фронт опрашивает статус. Синхронный HTTP-запрос на 20–60 секунд не проживёт.

## 7. Блиц-опрос

Третье действие по AI-сигналу, наравне с «подтвердить» и «отклонить».

1. AI генерирует вопросы по конкретной работе студента.
2. Ревьюер выбирает, какие отправить — **необязательно все**, количество адаптивно.
3. Работа уходит в статус `blitz_sent`, студент видит нейтральную формулировку «дополнительные вопросы по вашей работе» — **без упоминания сигнала**.
4. Студент отвечает текстом, срок 48 часов.
5. AI разбирает ответ и готовит рекомендацию.
6. **Решение по баллу принимает ревьюер.** Балл не меняется автоматически никогда (FR-045).

Если студент не ответил в срок — работа возвращается ревьюеру с пометкой «ответ не получен». Никакого автоматического снижения.

## 8. Распределение

Правило простое и объяснимое:

1. Фильтр по специализации.
2. Среди доступных — ревьюер с минимальной текущей нагрузкой (активные работы × вес трудоёмкости задания).
3. При равенстве — round-robin.
4. Жёсткий кап работ на ревьюера, параметр курса.

Каждое назначение сопровождается сгенерированной строкой объяснения: специализация, текущая загрузка, сколько кандидатов рассматривалось.

**Распределение — рекомендация.** Методист смотрит раскладку и применяет её одной кнопкой; может поменять руками. При любом изменении назначений флаги риска пересчитываются.

**Риск просрочки:** работа, не начатая за 24 часа до дедлайна, подсвечивается у методиста и триггерит уведомление. Переназначает человек. Автопилот с прогнозом риска — в дорожную карту.

> Многофакторная маршрутизация (сложность работы, уверенность AI, второе мнение, автоперераспределение) в прототип не входит — она разворачивает порядок стадий, поскольку требует результата AI-ревью до назначения. Показывается на слайде как развитие. Финальное решение по этому пункту — за владельцем фичи распределения.

## 9. Инфраструктура

Четыре сервиса плюс инфраструктурные, монорепо, общий `docker-compose`.

| Контейнер | Роль |
|---|---|
| `frontend` | Vue + nginx |
| `api` | FastAPI, весь домен, Postgres |
| `ai-worker` | Очередь, пайплайн ревью |
| `llm-gateway` | Абстракция модели |
| `postgres`, `redis` | Инфраструктура |

Домен **не режем** на review-service и assignment-service: за пять дней распределённые транзакции между ними съедят проект.

### llm-gateway

Единственный аргумент по блокеру «защищённый контур»: смена модели — это переменная окружения. Отдельный микросервис `ai-reviewer` использует официальный `zai-sdk==0.2.3`, модель задаётся через `ZAI_MODEL` (по умолчанию `glm-5.3-flash`), ключ — через `ZAI_API_KEY`. Core API не получает ключ провайдера и общается с AI reviewer только по внутреннему HTTP-контракту.

> Осторожно: ключи Coding Plan работают через отдельный эндпоинт `/api/coding/paas/v4` и не взаимозаменяемы с общим API.

**Кэш** живёт здесь: ключ — хэш (модель, промпт, параметры), хранилище — Postgres, флаг `LLM_CACHE`. Даёт три вещи: устойчивое демо, воспроизводимость прогонов Rubric CI и честную стоимость обработки.

Правило при недоступности провайдера: отдаём из кэша, при промахе — ошибка и работа человеку.

### Авторизация

Настоящий JWT и RBAC на эндпоинтах, вход на демо в один клик тремя кнопками.

**Инвариант, который проверяется, а не декларируется:** студенту эндпоинты AI-сигнала и черновиков не отдаются на уровне доступа, а не на уровне вёрстки. Это и есть «ни одно сообщение не уходит студенту без человека».

## 12. Защита данных

В прототипе работы уходят к внешнему провайдеру. Материалы `homework_examples` — учебные, не персональные данные.

Формулировка для защиты: **«в прототипе — внешний провайдер на учебных материалах; в проде — тот же интерфейс на модели внутри контура, смена одной переменной»**.

Анонимизация (вычистка имён, логинов, mattermost-name, путей с идентификаторами перед вызовом) — следующим шагом, слоем в `llm-gateway`.

## 14. Порядок отказа

Утверждён заранее, применяется переключением фиче-флагов. Режем сверху:

1. Course Debt Radar как интерфейс → остаётся слайдом
2. Аналитика расхождений AI и ревьюера → статичный экран по фикстурам
3. Telegram-бот → остаются in-app уведомления
4. Конструктор критериев → рубрика правится в JSON, прогон на golden set остаётся
5. Блиц-опрос → **не режется никогда**

**Три обязательные функции кейса и сквозной сценарий не режутся ни при каких условиях.** Дополнительных функций заявлено шесть при минимуме три — запас на отказ уже есть.

## 15. Что осталось за рамками этого документа

Решения ниже приняты владельцами соответствующих фич и здесь только зафиксированы:

- **Порядок реализации фич.** Команда идёт сверху вниз по своему списку приоритетов, где AI-конструктор стоит выше AI-ревью. Техническое замечание к сведению владельцев: прогон версии критериев на golden set вызывает пайплайн ревью, поэтому конструктор опирается на стадию `grade`. Кабинет к обоим готов — до появления модулей работает мок в том же контракте.
- **Глубина распределения** — простое правило против многофакторной маршрутизации.

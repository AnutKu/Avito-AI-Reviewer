1. Проанализировать описание ситуации в компании
Компания строит ML-платформу для централизованного доступа к GPU-ресурсам.
Масштаб: 85 продуктовых ML-команд, ~600 инженеров, ~11 000 задач в день на платформе.
Команды, вовлеченные в проект:
Команда DC – поддержка ЦОД и HW-ремонт: состоит из 23 человек, она привлекалась по мере надобности.
Командa ML-инфраструктуры: 5 человек (она же занималась поддержкой Slurm), была вовлечена в проект на 100%.
Команда Kubernetes: 12 человек (она тратила на поддержку и доработку ML-платформы 35% своего времени).
Команды разработчиков были вовлечены в проект, при каждом изменении инфраструктуры они теряли 10% своей эффективности в течении месяца, их участие в доработке инфраструктуры не оценивается.

Платформа обслуживает разные типы задач:
Команда рискового скоринга:
800 ГБ RAM + много CPU (какой порядок у “много” не совсем ясно: сотни, тысячи, десятки тысяч? Будем считать в среднем за “много” 1-2 тысячи cpu)
GPU не используется
Обрабатывает большие объемы данных с простыми моделями
ML-команды обучения моделей:
800 ГБ RAM + 8 GPU + 16 CPU
Одна задача = целый сервер
Два класса задач по модели вытеснения
Невытесняемые задачи:
Запускаются, отрабатывают, завершаются
Не могут быть прерваны в процессе
Используют ресурсы только в рамках квоты, их намеренно держат в меньшинстве
Подходят для критичных вычислений, которые нельзя прерывать
Вытесняемые задачи:
Могут быть остановлены в любой момент и отправлены обратно в очередь
Должны сохранять состояние при перезапуске (чекпоинты)
Могут занимать весь кластер, включая ресурсы сверх квоты
Сложнее в разработке, но дают гибкость в управлении ресурсами
Основной инструмент управления утилизацией кластера

2. Ключевые задачи и цели
Бизнес-цели:
Один общий пул GPU для всех команд вместо отдельных серверов – снижение затрат
Масштабируемость – платформа должна расти совместно с компанией, не требуя каждый раз перестройки инфры
Технические цели:
Квотирование с грануарностью меньше одного узла (дать команде 2 GPU из 8, а не целый узел)
Поддержка разнородных нагрузок – от задач без GPU с большим количеством CPU до GPU-задач на целый узел.
Сетевые политики (изоляция трафика между командами)
Нормальное вытеснение задач (освобождать ресурсы без потери прогресса)
Понятные приоритеты (гарантии, что важные задачи получают ресурсы вовремя)
Мониторинг и observability
Документация и комьюнити для развития платформы

3. Ключевые проблемы на каждом этапе
Slurm
Квотирование с гранулярностью один узел – неэффективная использование ресурсов при использовании менее 8 GPU на задачу
Отсутствие сетевых политик
Итог: Аллокация ~65%, утилизация GPU ~50%
Kubernetes (стандартные Jobs)
Дедлайны считались с момента создания, не с момента запуска
Не работало вытеснение задач
Планировщик плохо упаковывал задачи
Не было квотирования
Переход 1-ого кластера + 1-ого облака
Итог: Аллокация упала до ~50%, утилизация GPU до ~20%: переход ухудшил ситуацию
Kubernetes + собственный оператор и планировщик
Гонки между планировщиками
Дублирование логики
Простои кластера
Высокая стоимость поддержки собственного кода
Все кластеры переведены на k8s с кастомным планировщиком
Итог: Аллокация ~60%, утилизация ~30%: все еще хуже, чем Slurm
Kubernetes + Volcano
Потребовалась доработка вытеснения между проектами
Потребовалось добавление гарантированных квот
Аллокация ~70%, утилизация ~45%: +5% аллокации и -5% утилизации отн. Slurm (больше использованных ресурсов, но хуже использование самого дорогого ресурса – GPU, плохо ли это или хорошо сильно зависит от соотношения CPU-задач vs GPU-задач и интересов бизнеса)
Общие проблемы от переходов:
При каждой смене архитектуры кластер выводился из использования: 2 недели установки + 2 недели тестирования = 1 месяц простоя
Команды разработчиков теряла 10% эффективности в течение месяца после каждого изменения
В среднем 2 раза в неделю – привлечение DC-инженеров для ремонта оборудования

4. Какое open-source решение в итоге внедрила компания

Решение: Volcano – нативный планировщик для Kubernetes, ориентированный на ML-задачи.
Что даёт Volcano+Kubernetes:
Volcano:
Механизм управления: Gang Scheduling (все N подов или ничего) + Pod Group
Fair-share scheduling
Мониторинг
Гарантированные квоты
Kubernetes
Сервисы: инференс, API, пайплайны
Self-healing, auto-scaling
Богатая экосистема (Helm, Operators)
Multi-tenancy через RBAC + NS
Архитектурная схема:
Оператор создает задачу → она превращается в pod group → привязывается к очереди и квоте → планировщик решает, куда её ставить

5.10 Серые зоны
1. Сеть облако #2 (25GE, A100)
25GE не подходит для больших распределенных обучений. Эти 150 GPU по стуи пригодны только для инференсов или single-GPU задач. Что может тянуть утилизацию вниз.
2. Задачи рискового скоринга
Занимает GPU-узлы по CPU и RAM, но GPU при этом простаивают. Это искусственно снижает утилизацию GPU и завышает аллокацию без реальной GPU-работы.
3. Собственный оператор
Команда потратила квартал на разработку. Стоимость поддержки собственного кода не учтена в OpEx явно.
4. Цены H100/H200
В лекции явно дана только цена B200. Для H100/H200 используется допущение, что стоимость установки сравнима с стоимость установки b200 (что в реальности завышает расчеты), а стоимость самих узлов взяты из открытых источников.
5. Утилизация GPU внутри задач (MFU)
Даже на лучшем этапе 45% утилизации GPU без DCGM-профилирования неизвестно, какие именно задачи тянут среднее вниз. nvidia-smi может показывать загрузку 100%, а MFU сильно меньше.

6. Варианты оптимизации
6.1 Проводить предварительную аналитику готовых решений во избежание такого количества переходов
Пропуск этапов сэкономил бы ~$18M (см. п. 5.8)
Вывод: Slurm → Kubernetes + Volcano напрямую
6.2 Облако #2
150 A100 на 25GE не подходит для распределенного обучения.
Оптимальное использование: инферы, Single-GPU экспы, Dev/test среда
Не нужно тратить время на оптимизацию планировщика для этого кластера под распределенное обучение.
6.3 CPU-only кластеры
Возможно, для задач рискового скоринга стоит завести отдельные CPU-кластеры, что позволит не сжигать GPU-часы понапрасну.
6.4 Параллельная миграция, не последовательная
По условию: при идентичной сети тест не нужен. Можно было бы сгруппировать кластеры по типу сети и мигрировать группами параллельно, так бы удалось сэкономить еще по 2 недели простоя кластера для каждого перехода.
6.5 Автоматическая оптимизация гиперпараметров с т.ч. GPU
Внедерение инфраструктуры автоматически подбирающей batch_size, количество подов и прочего для максимизации использования ресурсов внутри джобы.
6.6 DCGM + алерты на низкий MFU
Без DCGM-профилирования команды не знают реальную утилизацию. Настройка алертов на SM occupancy < 30% позволит находить неэффективные задачи и работать с командами.
